# PORTING.md — правила портирования fallout2-ce → Java

## База

- Оригинал: `fallout2-ce/fallout2-ce` @ `d08c9ea` (ветка `main` в этом клоне).
  Апстрим не трогаем: наши файлы — только `java/`, `docker/`.
- Эталон поведения: `docker/refharness/golden/v*.txt`. Спорный случай —
  побеждает бинарь из контейнера, не память.

## Стиль (1:1, дифф читаем рядом с C++)

1. Пакет `org.fallout2ce`, класс на пару `.h/.cc`: `geometry.h` → `Geometry.java`.
   В шапке каждого класса — какие адреса/функции покрыты (`// 0x4C6C18`).
2. **Java first, без велосипедов из C++.** Идиоматичная Java по умолчанию:
   records, enums, foreach, стандартные коллекции, `AutoCloseable`,
   `StringBuilder`, `Optional`/nullable вместо out-параметров там, где это
   не меняет наблюдаемое поведение. 1:1 с C — только там, где поведение
   наблюдаемо: коды возврата, порядок обхода/сериализации, квирки,
   сайд-эффекты, точность форматов. `NOTE:` помечает каждое отклонение.
2. C-структуры с мутацией — mutable-классы с публичными полями (`Rect`);
   чистые данные — `record` (`Point`, `Size`).
3. Out-параметры — caller-provided объекты; коды возврата (`0`/`-1`) сохраняем.
4. `unsigned char` → `byte` + `Byte.toUnsignedInt` на чтении; 32-битная
   арифметика C — обычный `int` (проверить отсутствие переполнений в C!).
5. Глобалы `namespace fallout` — `static` поля/методы utility-класса.
6. `debugPrint` → `Debug.print` (slf4j, логгер `fallout`). Формат
   бэкенда — дело бэкенда, тесты assert'ят поведение, а не текст лога.
7. Баги оригинала портируем как есть + тест фиксирует (пример:
   `randomBetween(5,3)` всегда возвращает `min`).
8. Отклонения от C (хостед-RNG в `randomInit`, пул без лимита) — только там,
   где поведение ненаблюдаемо, и с `NOTE:` в коде.
9. Состояние игры/движка, которого ещё нет (`Game`, `Combat`, файлы, SDL) —
   injectable seams (`GameClock`, `CriticalsPolicy`, `initColors()→false`),
   дефолт = «свежая игра, день 0».

## Порядок портирования

1. Чистая логика без I/O (geometry, random, color, config-парсеры...).
2. Файловый слой (`db`/`xfile`/`dfile` → `java.nio`), затем данные (art, map, proto).
3. Платформа последней (SDL → LWJGL/обёртка; `svga`/`window`/`audio_engine`).

## Платформа (SPI)

- Бэкенды, которым нужны сторонние нативные библиотеки (SDL/OpenGL —
  будущие `svga`/`window`/`audio_engine`), живут в отдельных Maven-модулях
  и подключаются через `ServiceLoader`. Ядро (`engine`) их не видит.
- `f2j-platform-spi`: `VideoBackend`, `SystemClock`, `Sleeper`,
  `TickerRegistry`, `AudioBackend` (WAV-байты: one-shot/mузыка-луп/громкость),
  `PlatformPlugin` (только JRE-типы, ноль зависимостей; `audio()` по
  умолчанию silent).
- `f2j-platform-headless`: managed-null (`headless`, всё дропается).
  Для тихих/тестовых стендов: `-Df2j.platform=headless`.
- `f2j-platform-awt`: рабочий managed-рендерер (`awt`, только JRE: окно
  Swing, палитровый фреймбуфер 640x480, `component << 2` как в
  `directDrawSetPalette`). Выбор: `-Df2j.platform=awt`. Без дисплея окно не
  открывается, offscreen-пиксели сверяются пиксель-в-пиксель тестами.
  Встроенные пайплайны JRE при этом работают как обычно: offscreen-образ
  создаётся через `createCompatibleImage` (оптимален для текущего пайплайна
  — OpenGL при `-Dsun.java2d.opengl=True`, Direct3D, Metal), ничего не
  форсится и не отключается; проверка — `-Dsun.java2d.trace=log`.
- `f2j-platform-audio`: managed-звук (`audio`: `javax.sound.sampled`,
  деградация в silence без микшера; плюс явный `NullAudioBackend`).
- `f2j-platform-safe`: дефолт (`safe`): AWT-экран + sampled-звук +
  системные часы/слип. Именно он выбирается без флагов — игра из коробки
  работает только на managed-коде, без SDL/DirectX и сторонних нативок.
- `Platform.load()`: `-Df2j.platform=<name>` побеждает; иначе `safe`,
  если есть; иначе `headless`, если есть; иначе единственный провайдер;
  иначе (или при неизвестном имени) — fail fast.
- `engine` по умолчанию использует только managed-код (JRE + slf4j + SPI):
  встроенные no-op/system-дефолты швов + `headless` из коробки.
- `Platform.load()`: `-Df2j.platform=<name>` побеждает; иначе `safe`,
  если есть; иначе `headless`, если есть; иначе единственный провайдер;
  иначе (или при неизвестном имени) — fail fast. Без провайдеров остаются
  встроенные дефолты.
- Швы тестов (`Color.video`, `Ticks.clock`, ...) — те же SPI-типы;
  тесты присваивают фейки напрямую, `Platform.install/resetForTests`
  — для интеграционных проверок.
- Игровая логика по умолчанию wired на портированный managed-код
  (пример: `Palette.colorCycle` → `ColorCycle`), а не на no-op.

## Скрипты: компилятор и API

- Формат `.int`: код верхнего уровня (лаунчер) в начале файла, таблица
  процедур с 42, дальше идентификаторы и статические строки, в конце тела
  процедур. Процедура без тела имеет offset 0 — оригинал входит в неё
  как в лаунчер.
- `ScriptCompiler` (front end): декодер, анализ стека и ветвей по графу
  инструкций (не по прямой линии: прыжок оставляет код под собой, вызов
  — тоже, а возврат приходит через return stack). Декодер разбирает все
  1443 скрипта игры без ошибок; анализ расходится с оригиналом там, где
  у скрипта разная глубина стека в точке слияния — это свойство игрового
  кода, а не ошибка.
- `ScriptEmitter`: превращает форму скрипта в class-файл — подкласс
  `ScriptBase` (метод на процедуру, код скрипта и лаунчер). Файл класса
  пишется на ASM прямо в рантайме: ни исходника, ни компилятора в цикле
  нет. (ReflectASM не годится: опубликована только его access-часть, а
  генератор кода из репозитория автора убран.) Управление потоком
  разрешено: ветка — настоящий переход, билд-ин игры — прямой вызов
  `GameApi` (интерфейс, поэтому `invokeinterface`). Скомпилированный
  класс лежит в своём пакете и в своём загрузчике, поэтому унаследованные
  `protected`-члены `ScriptBase` вызываются через имя подкласса — так
  же, как это делает javac. `goto` в байткоде есть, и блоковая
  диспетчеризация не нужна.
- Тип значения, которое кладёт `PUSH`, зашит в сам опкод (`0xC001` — int,
  `0xA001` — float, `0x9001` — статическая строка), и компилятор его
  разбирает: строка остаётся строкой со своим смещением в таблице файла.
- Порядок операндов: интерпретатор снимает два значения со стека, и
  верхнее из них — правый операнд, а нижнее — левый. `value[1] op value[0]`
  в оригинале — это «нижнее над верхним». Скомпилированный код сначала
  клал операнды наоборот, и вычитание, деление, остаток, сравнения на
  «больше-меньше» и сложение строк считались наоборот.
- `ScriptBase` — состояние скрипта: стек значений, стек возвратов, frame
  pointer, локали, куча строк, ссылка на API. Собственное состояние
  скрипта (self, локальные переменные, action) живёт здесь, а не в API.
  Куча строк — блочная, блок в блок как `programPushString` (0x467A80):
  те же чётные выравнивания, тот же обход с дедупликацией, тот же
  0x8000-терминатор, поэтому смещения динамических строк у
  скомпилированного кода те же, что у интерпретатора.
  Внешние переменные (0x14/0x15/0x16) — общий с другими скриптами
  реестр `Export`, а не API; имя внешней переменной даётся смещением
  внутрь таблицы имён, а не её началом, поэтому имя читается из таблицы,
  а не ищется в ней. Ошибка в них останавливает скрипт так же, как в
  интерпретаторе.
- Проверка: `ScriptEmitterTest` гоняет эталонные скрипты через
  скомпилированный код и через интерпретатор и сверяет след вызовов и
  финальный стек — и против mock'а, и против игровой реализации API.
  Отдельно сверяются скрипты, которые делят внешние переменные.
  `CompiledSweepTest` гоняет через оба движка все 1443 скрипта игры.
  Эмиттер покрывает все 1443 скрипта без единой непреведённой инструкции,
  и 1442 из них ведут себя одинаково — с одним исключением:
  - `KRUPPER.int` возвращается на адрес, который не является адресом
    возврата вызова: интерпретатор прыгает туда, а скомпилированный код
    не умеет прыгать на адрес, о котором он не знает при написании.
  (`HUNTER.int` и `ROMERO.int` раньше расходились смещением динамической
  строки: интерпретатор держал их в блочной куче, скомпилированный код —
  списком с другим номером. Теперь куча скрипта — та же блочная, и оба
  сходятся.)
- `GameApi` — интерфейс билд-инов игры (161 штука). Он не зависит от
  интерпретатора: скомпилированный скрипт получает любую реализацию —
  игру, mock или декоратор-логгер. `MockScriptApi` записывает вызовы,
  `UnsupportedScriptApi` отказывает, `GameScriptApi` — игра.
- Игра даёт все 161 билд-инов из `GameApi` (ни один опкод больше не
  останавливает скрипт). Тайлы мира спарсены (`[worldmaptiles]`,
  golden/v145: сетка 4×20, мир 1400×1500, поля тайлов, террейн
  `Desert/Mountain/City/Ocean` со случайными картами, заголовки 76
  таблиц встреч, скаляры и субзаписи их записей, база энкаунтеров
  (`Encounter: <имя>`: ratio/pid/дистанция/тайл/предметы/скрипт/
  команда/формация), условия (`if(...)`: random/global/player(level)/
  days_played/time_of_day/enctr(num_critters) с операторами и связками
  and/or) и 42 субтайл-строки каждого тайла (террейн/fill/шансы
  встреч/тип встречи; v146). Дальше в мире: движение партии.
- Аргумент-`value` (не строка, а `ProgramValue`) игра читает сама: у
  интерпретатора строка лежит в куче программы, у скомпилированного
  скрипта — в куче скрипта. Сейчас таких билд-инов у игры нет, но когда
  они появятся, интерфейсу понадобится доступ к куче того скрипта,
  который вызвал билд-ин.

## Проверка

```powershell
mvn -pl engine test          # из java/
powershell -File docker/refharness/check-refharness.ps1  # эталон цел
```

Тесты на реальных DAT (`DBaseTest.realMasterDat/realPatchDat`) берут
каталог из `F2J_GAMEDATA` (`.../game-en`) и abort'ятся без него.
Новый модуль = векторы в харнес (`ref_main.cc` + `golden/vN.txt`) ДО Java-класса.

### Прототип игрока

- В C++ gDude (src/object.h:24) **не присваивается** нигде в движке: поиск по всем
  147 .cc дал только mapper.cc (редактор карт). Игрока создаёт игровой код, которого
  в src/ нет, поэтому портировать создание «как в C» нельзя — прототип игрока берётся
  из данных игры.
- pid устроен как (тип << 24) | номер файла прото: так у собаки 16777558
  (0x01000156) файл 00000342.pro — младшие 24 бита это номер файла, а не индекс
  в списке.
- Списки прото лежат в master.dat: proto\<тип>\<тип>.lst (например
  proto\critters\critters.lst), сами .pro — в preload.dat. Папки premade в
  данных нет.
- Имена прототипов лежат в message stack игровой фазы, поэтому ProtoDb.protoGetName()
  возвращает null и найти прототип игрока по имени «Player» пока нечем.
### Статы игрока в харнессе

- Секция [partyobjects] эталонного харнесса печатает базовые статы игрока:
  dude-str=5 dude-agi=5 dude-luck=5 (golden v138.txt). Это числа **после**
  сброса прото игрока: в C++ их ставит _ResetPlayer →
  protoCritterDataResetStats (src/stat.cc:707, значения из
  gStatDescriptions[stat].defaultValue), а он живёт в игровой фазе
  (создание персонажа/новая игра).
- Порт этот сброс не делает, поэтому Stat.critterGetBaseStat(dude, ...)
  читает сырое прото из 00000000.pro и возвращает 0. Расхождение
  зафиксировано вектором в харнессе; чтобы его закрыть, нужно портировать
  protoCritterDataResetStats (src/stat.cc) и решить, дергать ли его без
  игровой фазы.- Уточнение после проверки: gDudeProto в C++ — не файл, а **статическая таблица**
  (src/proto.cc:92): fid 0x1000001, флаг LIGHT_THRU, sid = -1,
  baseStats из 35 значений (5,5,5,5,5,5,5 + производные 18/23/100).
  Порт теперь инициализирует ProtoDb.dudeProto этой таблицей, поэтому статы
  игрока совпадают с вектором (5/5/5). _ResetPlayer →
  protoCritterDataResetStats нужны только для сброса/редактора персонажа и
  остаются на игровую фазу.- Ветка игрока в op_critter_inven_obj (0x8106) перенесена: у игрока предмет
  отдаётся только из руки, которую держит интерфейс (Interface.interfaceGetCurrentHand),
  вторая рука пуста — как в C (src/interpreter_extra.cc, opCritterGetInventoryObject).
  Проверка с предметом «в руке» у критера (не игрока) сделана: объект в инвентаре и его флаг IN_RIGHT_HAND — одно и то же, как в C.
### Последние билд-ины и их швы

Все 161 билд-инов, объявленных в `GameApi`, отдаются игрой. Последние
два упирались в мировую карту — теперь тайлы мира спарсены
(`WorldmapTiles`, векторы `[worldmaptiles]` golden/v139), и оба живут:

- op_mark_area_known (0x80B2): область снимается с карты и ставится на
  неё (`wmAreaSetVisibleState`), а отметка посещённости
  (`wmAreaMarkVisitedState`) пишет сетку субтайлов — кольцо вокруг
  посещённой метки становится known, сама метка visited; визит
  неизвестной области ложится как known (квирк оригинала). Карта
  помечает свою область (`wmMapMarkVisited`). До загрузки тайлов
  (`WorldmapTiles.wmTilesInit`) отметка останавливается на поиске
  субтайла.
- op_wm_area_set_pos (0x80E5): позиция проверяется по границам тайлов
  — мир 1400×1500 из `data\worldmap.txt`; внутри двигает, вне и до
  загрузки отказывает.
- op_metarule (0x810B) реализован для всех правил: партия, очередь
  (DRUG), навык-тег, фильтры, тип убийства, инвентарь
  (`DROP_ALL_INVEN` 42, `INVEN_UNWIELD_WHO` 43, `WEAPON_DAMAGE_TYPE` 49,
  `CRITTER_BARTERS` 50), флаги игры (`SIGNAL_END_GAME` 13,
  `FIRST_RUN` 14, `IS_LOADGAME` 22), машина (`CAR_CURRENT_TOWN` 30,
  `GIVE_CAR_TO_PARTY` 31, `GIVE_CAR_GAS` 32, багажник 52/53), лифт
  (`ELEVATOR` 15, через `ScriptsState.scriptsRequestElevator` и поиск
  стаба `ElevatorStub` рядом) и мир — `AREA_KNOWN` (17), `MAP_KNOWN`
  (19), `GET_WORLDMAP_XPOS/YPOS` (44/45) и `CURRENT_TOWN` (46); чтения
  мира на `[worldmaptiles]` golden/v141 (стартовая позиция 173,122,
  область не задана до движения партии).
- op_get_pc_stat (0x80A6) отдаёт статы игрока как персонажа из
  перенесённого стат-движка (`Stat.pcGetStat`; домен PcStat уже был
  в `Stat.java` с векторами `[pcstat]`).
- op_kill_critter_type (0x80EE) реализован для убийства без анимации.
- op_critter_mod_skill (0x813C) меняет навык игрока через
  перенесённые `Skill.skillAddForce`/`skillSubForce` (правка уходит
  в кэшированное прото, как указатель в C); интерфейс после правки
  не обновляется — интерфейс не портирован.
